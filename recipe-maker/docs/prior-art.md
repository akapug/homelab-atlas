# Recipe Maker prior art

Assessment date: **2026-10-24**. Recipe Maker source snapshot: **`9b9d9e8d63b6abbe01add20dc9fa957aa0484581`**. Source line references below refer to this snapshot, not an uncommitted checkout. External source references use dated commits or releases where available.

## Verdict

**Recipe Maker is a useful, technically serious engineering prototype. Its research novelty is UNPROVEN.** It already does substantially more than a VRAM calculator: it joins tensor and expert placement, quantization/quality estimates, measured kernel and memory behavior, CPU/PMem limits, launch checks, and predicted-versus-observed evidence. Calling this amateur work would overlook those implemented mechanisms. Calling its solver or roofline reasoning a new research algorithm would overlook substantial prior art.

The most defensible potentially distinctive contribution is the **integration and reproducible evaluation of heterogeneous, memory-constrained hardware**, especially CPU-heavy inference, Intel GPU backends, NUMA, persistent memory, workload-specific expert heat and cross-box transfer costs. These are useful comparison axes, not proof that nobody has combined them before. A publishable contribution needs matched baselines, ablations and held-out results. Neither the existence of an unusual hardware combination nor a growing feature list establishes novelty.

**Recommended direction:** keep the existing planner, evidence model and run ledger; borrow stronger calibration and search methods behind one small interface. Do not replace them with an RL training stack. Confidence in this source-based direction is **90%**; the performance advantage of any proposed tuner remains an experiment, not an established result.

This is a source-reading and documentation assessment. No builds, dependency installations, model runs, GPU operations or reproduction of external benchmarks were performed. Published benchmark results are authors' results under their stated conditions, not measurements made for this assessment. No private run transcripts or raw research exports are included.

### Important validation distinction

`winFit` fits stage constants on points labeled `fit`, but estimates pipeline efficiency `eta` from **all points with throughput** (`src/model.js:2218–2251`, specifically `2239–2240`). This includes actual check cells **`V0-n2` and `V0-n32`** in `data/window/odie-fnx-2xb70.json:235–276`: both declare `use: check` and reference retained aggregate-throughput operands. Those operands were confirmed present in the snapshot's ledger without exporting the run text. `build.py:2031–2040` attaches that throughput to each point before the fit. Therefore their printed throughput errors are not fully independent end-to-end holdouts: the observations also help set `eta`. Their stage checks can still be informative because stage-constant fitting selects `use: fit` at `src/model.js:2222`. This is a component-versus-whole-model validation distinction, not evidence that the measurements are false. Relabel the partially in-sample throughput checks or fit `eta` on training-only points and evaluate the others unchanged; preserve the genuine scoped decode/dLLM holdouts.

The documented accuracy figures are dated summaries, not fresh measurements. `docs/how-it-works.md:507–569` explicitly reports small cells, worsening error for some newer builds, limited prefill envelopes, borrowed terms, quality fits with very few degrees of freedom and large external errors in some hardware classes. Those admissions materially strengthen the engineering honesty while limiting a general predictive-accuracy claim.

## 2. Placement and configuration planners

**Reading key:** “not established” means the cited implementation or documentation did not prove the capability; it does not mean impossible. A CPU listed next to an NVIDIA GPU does not establish Intel **GPU** support. Generic host RAM is not an explicit Optane/NUMA bandwidth model. Multigpu is not automatically multibox. Paper claims, released code and measured coverage are separate evidence classes.

### FlexGen / FlexLLMGen

**Prior art:** the [FlexGen paper](https://arxiv.org/abs/2303.06865) (2023) formulates offloading policy optimization with linear programming across GPU, CPU RAM and disk, covering weights, activations and KV, batch size and compression. Its main objective is high-throughput, latency-insensitive inference. This is direct prior art against any claim that automatically planning capacity and transfers across these tiers is new.

**Implementation check:** the archived official release exposes a concrete [`Policy`](https://github.com/FMInference/FlexLLMGen/blob/004ffef82b46e8dc8685c55d0cdda650bdaf1269/flexllmgen/flex_opt.py#L33-L78) with manual weight/cache/activation percentages, GPU microbatch size, number of microbatches and CPU attention choices. Its [README/FAQ](https://github.com/FMInference/FlexLLMGen/blob/004ffef82b46e8dc8685c55d0cdda650bdaf1269/README.md) says the automatic cost model and policy optimizer are not released there. Standalone [`profile_bandwidth.py`](https://github.com/FMInference/FlexLLMGen/blob/004ffef82b46e8dc8685c55d0cdda650bdaf1269/flexllmgen/profile_bandwidth.py) and `profile_matmul.py` measure transfer/compute behavior; do not mistake their presence for a wired automatic LP service.

The released implementation is CUDA/OPT-oriented. CPU-heavy attention is relevant, but Intel XPU and separately calibrated Optane support are not established. Distributed execution exists in `dist_flex_opt.py`; arbitrary heterogeneous multibox behavior is not thereby validated. **Borrow** the explicit policy variables and capacity/transfer accounting; **skip** adopting this archived runtime as the Recipe Maker search engine. Snapshot `004ffef82b46`, 2024-10-28.

### MoE-Lightning

The [2024-11-18 paper](https://arxiv.org/abs/2411.11217) and its [full text](https://arxiv.org/html/2411.11217v1) describe a Hierarchical Roofline Model, CPU–GPU–I/O pipelining, paged weights and offline MILP policy selection. Inputs include analytically counted operations/bytes and profiled compute, local-memory and inter-tier bandwidth ceilings. Decisions include total/microbatch sizes, CPU/GPU attention/FFN placement and resident fractions of weights/KV. CPU/GPU capacity and double-buffer staging matter. Decode CPU attention and GPU FFNs are evaluated for throughput-oriented MoE workloads.

This is especially relevant to Recipe Maker's batched window and overlap laws. The reported larger-model experiments use 2–4 T4s, but the stated formulation omits inter-GPU/inter-node communication; that is not a validated heterogeneous network planner. The described implementation requires the model to fit in host RAM rather than providing a disk-backed execution tier. Intel GPU and explicit Optane support are not established.

**Source availability limit:** the [author project page](https://pschafhalter.com/moe-lightning/) links `caoshiyi/FastMoE`; that endpoint returned 404 during this assessment. No official executable planner artifact was verified. Treat this comparison as **paper-backed**, not code-reproduced. **Borrow** the compute-near-data crossover, staged-transfer constraints and batch-dependent roofline; do not promise a drop-in library.

### Fiddler

[Fiddler](https://arxiv.org/abs/2402.07033) (2024) is direct prior art for executing cold MoE experts on CPU while keeping selected experts on GPU, moving activations instead of full expert weights. The [official source](https://github.com/efeslab/fiddler/blob/227715bfd6e8c731b29548eab01d9919c4fe9564/src/fiddler/mixtral.py) is narrower than a general hardware planner: `set_expert_loc` has a profiled popularity ordering, `calc_n_expert_on_gpu` uses free GPU capacity, and the CPU/GPU scheduling costs use constants (`latency_cpu = 7`, `latency_gpu = 70`, lines 37–39). Lines 351–361 size resident experts with a fixed memory margin. These are not portable measured calibration procedures.

The [README](https://github.com/efeslab/fiddler/blob/227715bfd6e8c731b29548eab01d9919c4fe9564/README.md) evaluates Intel Skylake/Cascade Lake CPUs with NVIDIA GPUs for unquantized Mixtral and emphasizes batch-one inference. A general KV-budget optimizer, explicit PMem tier, Intel GPU backend and multibox search are not established. **Borrow** activation-versus-weight transfer and CPU/GPU crossover baselines; **skip** porting its fixed costs or model-specific runtime into the planner. Snapshot `227715bfd6e8`, 2024-04-28.

### KTransformers

The [official project](https://github.com/kvcache-ai/ktransformers/tree/a694e718e8b3ec2e221277d674e369f3be38d2a4) is a valuable **execution backend and operator-placement reference**, not evidence of a general adaptive configuration optimizer. It has CPU expert kernels and phase-specific operator replacements. For example, the archived [XPU DeepSeek configuration](https://github.com/kvcache-ai/ktransformers/blob/a694e718e8b3ec2e221277d674e369f3be38d2a4/archive/ktransformers/optimize/optimize_rules/xpu/DeepSeek-V3-Chat.yaml) explicitly maps decode experts to CPU and prefill experts to XPU; dense/attention operators use XPU. That file's archived location and the documentation's older command paths matter when assessing current integration work.

Unlike many CUDA-only comparators, its [Intel XPU beta documentation](https://github.com/kvcache-ai/ktransformers/blob/a694e718e8b3ec2e221277d674e369f3be38d2a4/doc/en/xpu.md#L1-L6) explicitly names Arc A770/B580 and Xeon testing. It also states [serving is not supported on that Intel GPU path](https://github.com/kvcache-ai/ktransformers/blob/a694e718e8b3ec2e221277d674e369f3be38d2a4/doc/en/xpu.md#L87-L88). This does not prove another Arc model, current build or service works. AMX results are not transferable to older CPUs lacking AMX; AVX support needs its own measured kernels. Multi-GPU configurations are present, but a calibrated Optane/multibox search is not established. **Reuse** supported kernels/backends through sourced capability rows; **borrow** phase-specific execution identities. Do not label its SFT/DPO training features an RL placement tuner. Snapshot `a694e718e8b3`, 2026-10-19.

### HybriMoE

The [DAC 2025 paper](https://arxiv.org/abs/2504.05897) (submitted 2025-04-08) adds hybrid CPU/GPU scheduling, prefetch and cache management. The [official implementation](https://github.com/PKU-SEC-Lab/HybriMoE/blob/508a85b9a43dff37124370d8816e411e74827803/ktransformers/operators/experts.py) has routing-score-based priorities (`679–704`), prefetch/cache mechanisms and CPU/GPU queue-time comparisons (`1154–1176`). Crucially, its `model_cpu_time`, `model_gpu_time` and `model_move_time` (`1184–1201`) contain fixed formulas/constants with “need to be tested” comments. The paper's scheduling idea is not proof of a portable measurement-calibrated model in this artifact.

Its [setup](https://github.com/PKU-SEC-Lab/HybriMoE/blob/508a85b9a43dff37124370d8816e411e74827803/README.md) requires CUDA and demonstrates DeepSeek-V2-Lite GGUF. Runtime routing makes token/batch count relevant; no general cross-box/KV-capacity configuration optimizer or explicit Optane/Intel GPU support was established. **Borrow** dynamic cache-policy and routing-drift baselines; measure CPU/GPU/transfer curves instead of copying its constants. Snapshot `508a85b9a43d`, 2025-12-15.

### NVIDIA AIConfigurator, Dynamo, and the 2026 AISimulate successor

The [AIConfigurator paper](https://arxiv.org/abs/2601.06288) (2026) is direct configuration-planning prior art. Its [dated source](https://github.com/ai-dynamo/aiconfigurator/tree/f254959eb89e2f206b8f9a77051644d7c1cbdb89) combines measured operation performance, model/system specifications, memory accounting and search over serving parallelism, batches and prefill/decode workers under TTFT/TPOT constraints. [`sdk/sweep.py`](https://github.com/ai-dynamo/aiconfigurator/blob/f254959eb89e2f206b8f9a77051644d7c1cbdb89/src/aiconfigurator/sdk/sweep.py#L9-L15) owns aggregated/disaggregated search. The actual [performance database](https://github.com/ai-dynamo/aiconfigurator/blob/f254959eb89e2f206b8f9a77051644d7c1cbdb89/aic-core/src/aiconfigurator_core/sdk/perf_database.py#L1238-L1259) distinguishes silicon/formula modes and shared-row provenance; the shorter Python SDK file is a compatibility alias, not the implementation.

Its dated [hardware table](https://github.com/ai-dynamo/aiconfigurator/blob/f254959eb89e2f206b8f9a77051644d7c1cbdb89/README.md#supported-hardware) lists NVIDIA data-center systems and explicitly separates measured coverage from estimate-only specifications. This is not validated older CPU/Optane/XPU placement. Multi-GPU and serving communication models are relevant, but they target a different deployment regime. Dynamo Planner's [rapid versus thorough profiling](https://docs.dynamo.nvidia.com/dynamo/reference/components/planner-configuration) is a useful estimate-then-measure pattern, not itself proof of our hardware support. This last documentation URL is mutable; the pinned implementation is the stronger version witness. AIConfigurator snapshot `f254959eb89e`, 2026-09-09.

**A real newer release exists:** [AISimulate v0.13.0](https://github.com/ai-dynamo/aisimulate/releases/tag/v0.13.0) was published **2026-10-21**, following v0.12.0 on 2026-09-17. It succeeds the maintenance-only AIConfigurator line. Its [release-tagged README](https://github.com/ai-dynamo/aisimulate/blob/v0.13.0/README.md) separates forward-pass estimator coverage from end-to-end accuracy. Its [whole-forward contract](https://github.com/ai-dynamo/aisimulate/blob/v0.13.0/docs/perf-model/methods/whole-forward.md#L8-L21) consumes measured Parquet data with a required metadata sidecar and exact model/system/backend/parallelism/precision identity; direct silicon mode requires measured cells or supported brackets rather than unmeasured extrapolation. A [Rust implementation](https://github.com/ai-dynamo/aisimulate/blob/v0.13.0/crates/core/src/lib.rs#L18-L25) supplies perfmodel and replay components.

The release includes restricted GPU/host/storage KV offload modeling, not a general PMem expert-placement solver: storage KV offload is limited to aggregated vLLM prediction with attention DP 1 and specified exclusions. Binary packages for Linux and Apple Silicon do not prove inference-model calibration for those machines. **Borrow** the collector/data contract, operation/whole-forward decomposition, explicit coverage matrix and latency-constrained search. **Consider an offline comparator adapter** for a genuinely matched NVIDIA workload; **skip** replacing Recipe Maker's heterogeneous tier model with NVIDIA defaults. Python/Rust/native tooling and the larger serving ecosystem are real integration costs. Do not treat planned v0.14 features as available.

### BentoML llm-optimizer

The [official tool](https://github.com/bentoml/llm-optimizer/tree/7be87d776e60a978516a2ae53e4a4ff745d04c20) generates serving configurations, launches benchmarks and filters performance/SLO results for vLLM and SGLang. [`tuning/generation.py`](https://github.com/bentoml/llm-optimizer/blob/7be87d776e60a978516a2ae53e4a4ff745d04c20/src/llm_optimizer/tuning/generation.py) builds parameter ranges and TP/DP combinations; [`tuning/strategy.py`](https://github.com/bentoml/llm-optimizer/blob/7be87d776e60a978516a2ae53e4a4ff745d04c20/src/llm_optimizer/tuning/strategy.py) supplies framework-specific conservative/aggressive/memory-efficient configurations. This source supports a structured configuration/benchmark sweep claim, not an RL or Bayesian-search claim.

Batching, concurrency, quantization and latency metrics matter here, but its published hardware/configuration path is NVIDIA-serving oriented. CPU expert kernels, separately calibrated PMem/NUMA tiers, Intel GPU operation and heterogeneous multibox placement are not established. Benchmarking candidates supplies measurements; it is not identified calibration of each physical term. **Borrow** objective/SLO definitions and framework-specific conditional parameter generation; **skip** importing its launch lifecycle beside the existing recorder. Snapshot `7be87d776e60`, 2026-10-20.

### Strata: identify the project before comparing it

Several unrelated projects use this name. This comparison specifically concerns **[`mehbul/strata`](https://github.com/mehbul/strata/tree/e8647a84bac93cc2fae5f620726621e56fbc9659)**, a Rust planner/tuner around llama.cpp with an AMD/Windows-oriented documented path. It is not a claim about every engine named Strata.

Its [`placement.rs:79–145`](https://github.com/mehbul/strata/blob/e8647a84bac93cc2fae5f620726621e56fbc9659/src/placement.rs#L79-L145) is explicit: subtract dense/KV bytes, greedily fill VRAM then RAM. `disk_experts` describes weights left to fault from the mapped file, not an implemented managed disk tier. Its [`tune.rs`](https://github.com/mehbul/strata/blob/e8647a84bac93cc2fae5f620726621e56fbc9659/src/tune.rs#L204-L258) evaluates a coarse CPU-expert-layer grid including a derived starting point, then neighbors of the winner. It scores combined prefill/decode wall time for a documented long-input/shorter-output workload and keys saved tuning by context/KV type (`62–76,90–109`). That is a concrete, inexpensive baseline Recipe Maker should beat before adopting a sophisticated learner.

It does not establish calibrated bandwidth/compute/heat/quality optimization, explicit Optane, Intel GPU or multibox support. It measures candidate end-to-end performance rather than fitting a general physical model. **Borrow** context-keyed results, the workload-weighted objective and coarse-to-local measured search. Do not confuse this with Recipe Maker's existing engine labels or claim it validates those engines. Snapshot `e8647a84bac9`, 2026-08-29.

### llama.cpp and ik_llama.cpp automatic fitting

In mainline llama.cpp, [`common/arg.cpp:2765–2789,2889–2950`](https://github.com/ggml-org/llama.cpp/blob/3f03b17724ad8b69040825f45c43c59b092a0244/common/arg.cpp#L2889-L2950) actually defines `--fit`, `--fit-print`, `--fit-target`, `--fit-ctx`, manual tensor overrides and CPU-MoE controls. [`common/fit.cpp`](https://github.com/ggml-org/llama.cpp/blob/3f03b17724ad8b69040825f45c43c59b092a0244/common/fit.cpp) uses model/context memory breakdowns and backend device-memory reports to fit unset parameters, including GPU offloading and context. It can split layer fractions and distinguish sparse MoE weights. Unknown GPU memory is not silently treated as available (`118–125`).

In ik_llama.cpp, [`common/common.cpp:2414–2416,2464–2472,3603–3606`](https://github.com/ikawrakow/ik_llama.cpp/blob/804ee29c28a5e892df6e84941cb78628ed4c266c/common/common.cpp#L3603-L3606) implements `--fit` and fit-margin controls. The source describes `--gpu-fit-margin` as **layer-id/margin pairs**, a useful warning against blindly trusting a differently worded parameter document. No literal `--auto-ot` option was verified in the inspected argument implementations; do not invent that flag. Automatic tensor placement and a literal flag named auto-ot are different claims.

These are genuine **runtime fit baselines**, not measured throughput/quality optimizers. Mainline's backend abstraction can reach SYCL and CPU, but a particular model/backend must still report correct allocations and support the operators. Neither fitter establishes an explicit Optane bandwidth tier or network-optimal multibox placement. **Reuse** actual engine fit/allocation reports as feasibility evidence, keeping requested versus effective settings in the captured recipe. Do not copy their memory estimator and let it drift separately. Mainline snapshot `3f03b17724ad`, 2026-10-24; ik snapshot `804ee29c28a5`, 2026-10-23.

### GGUF parsers and VRAM calculators

[`gpustack/gguf-parser-go`](https://github.com/gpustack/gguf-parser-go/tree/9257743a3c1775b882ba1b58ec7f5a856c2cc385) is a stronger baseline than weight-size arithmetic. [`file_estimate__llamacpp.go`](https://github.com/gpustack/gguf-parser-go/blob/9257743a3c1775b882ba1b58ec7f5a856c2cc385/file_estimate__llamacpp.go#L79-L168) tracks per-device weights, KV and computation allocations and exposes an experimental maximum-token-rate estimate; it accepts offload, cache/batch and RPC-device settings. An RPC allocation estimate is not an end-to-end network benchmark. **Borrow/reuse as an independent estimator comparator**, feeding the existing model-intake and allocation checks; keep Recipe Maker's actual engine allocation receipts authoritative. ### Why not start with RL?

A static recipe evaluation is normally a constrained black-box experiment: propose a configuration, pay minutes, observe performance and quality. Bayesian optimization, model-assisted constrained search, racing and a good analytical candidate generator directly address that scarce-evaluation regime. Cheap exhaustive or coarse-to-local search remains an important baseline when the valid space is small. No cited library is guaranteed to win before measuring it.

RL becomes plausible when the actual problem is **sequential control**: cache eviction/prefetch, request routing or admission whose action changes future state, with workload drift and delayed costs. Then the state/action/reward and safe fallback must be defined, and a simulator or inexpensive environment must supply enough trustworthy episodes. A contextual bandit may suffice if there is no meaningful long-term state. Training a language model with PPO/GRPO/DPO, evaluating agent benchmarks, or using an RLHF framework does not solve this placement problem by itself.

A policy trained on an inaccurate simulator can optimize its errors. First validate whether dynamic control beats a static heat-based plan and measured crossover rules. Only then compare RL against those rules and a bandit under the **same evaluation and safety budget**.

## 4. One search boundary, no new competing harness

The appropriate proposed extension is library-agnostic. Preserve the existing JavaScript physics, recipe JSON, gate, recorder and accuracy reporter. An optional Python adapter may call the existing CLI; it should not reimplement `context`, `predictRecipe` or the feasibility checks.

- **Suggest:** `(space, immutable history, remaining evaluation budget) -> candidate recipe(s), method/version/seed, rationale`. The analytical frontier and coarse/local perturbations are candidate sources, not fake measured rewards.
- **Admit:** the existing `checkRecipe` / `report.js --check --strict --json` checks capability, allocations and quality requirements. Analytical infeasibility, unknown evidence, runtime OOM, timeout, numerical failure, interference and success are distinct outcomes. Some experiments may deliberately investigate unknowns, but such admission needs an explicitly recorded research policy rather than silently weakening strict checks.
- **Measure:** the existing launcher captures the effective recipe and launch prediction. The existing recorder appends the outcome and references retained evidence. A search adapter may index ledger IDs in its own sampler state; it must not become another ground-truth run ledger.
- **Observe:** `(trial identity, outcome, fidelity, duration, metrics, uncertainty, ledger ID)`. Failed arms are informative but never zero-latency successes. A crash is not automatically physical infeasibility; attribute harness errors separately.

The trial identity must include the **effective** engine/build, hardware/driver/backend, model/quant/store, placement, context/KV, batch/concurrency, draft/quality-relevant controls, workload and metric definition. Hash or otherwise version the built data and calibration/training split. Recipe names are labels, not complete identities. Reboots, driver changes and new engines can invalidate transfer of observations.

For minutes-per-arm work, count **elapsed evaluation time and interference cost**, not just candidate count. Keep budget, warm-up/repeat policy, fidelity levels and stop criteria in named configuration, not scattered literals. A useful fidelity ladder could be analytical rejection, isolated kernel/short run, representative request mix, then held-out end-to-end/quality evaluation. These are different measurements: establish rank correlation before using cheap levels to prune expensive ones. Changing batch, context or cache state can reverse the ranking.

Replicate promising and borderline arms; record timing spread and block/randomize order where practical. Model co-tenancy and thermal/driver changes as strata or exclusions, not ordinary independent Gaussian noise. Optimize a small declared objective set: for example per-client latency/accepted-token rate subject to quality and memory limits, with energy/total throughput as separate Pareto dimensions where measured. KLD, top-1 agreement and task success are not interchangeable units. Neither are device-only power and all-box wall power.

**No dependency is adopted here.** Compare a dependency-free analytical-plus-local baseline with **one** optional sampler, initially Optuna or SMAC, rather than importing all the listed frameworks. Search libraries can run locally without a hosted service. Pin dependencies and disable optional dashboards/telemetry/network downloads during trials; audit actual installed behavior rather than inferring no-egress from a local API. BoTorch adds large numerical dependencies; Ray adds processes/scheduling; TVM/Triton/Kernel Tuner add compiler/backend coupling. These costs can outweigh a marginal reduction in arm count. Existing remote model intake is a separate, explicit data-fetch boundary, not a reason for tuning to require network access.

## 6. Three highest-value upgrades

The order favors decisions that make later expensive experiments trustworthy. Costs are expressed in work and measurement units because no implementation or hardware timing study was authorized for this assessment. These are proposals, not claimed delivered capabilities.

### 1. Freeze calibration cohorts and measure decision error

**Change.** Extend the existing evidence/fit/accuracy paths with a data-and-split identity covering every fitted term. Separate training, component checks and genuinely untouched end-to-end checks. In particular, either fit window `eta` using training data only or label throughput checks that contributed to it as partially in-sample. Add held-out rank accuracy, feasibility false-negative/false-positive rates and decision regret alongside absolute prediction error. Retain scope refusals and the existing decode/dLLM holdouts.

**Reuse/seam.** `build.py` input selection and backend line fitting; `src/model.js` calibration, `recipeDecodeFit`, `winFit` and existing holdout exclusions; `src/accuracy.js` and `report.js --accuracy/--window`. Borrow AISimulate's exact-cell metadata contract and explicit coverage-versus-accuracy distinction. Use hierarchical roofline terms where compute/transfer ambiguity currently sits in a residual; do not add an unidentified parameter for every arm.

**Cost.** Schema/report/fixture work plus independent measurements for previously untested cells. Let `R` be the number of required representative cells, `P` the configured repetitions and `T` the measured time per arm: the main runtime cost is approximately `R × P × T`, plus warm-up and quality evaluation. Retained manifests are small; raw traces remain outside git. Freezing inputs must not prevent deliberate, versioned recalibration.

**Evidence gap.** There is no source-based estimate of out-of-build generalization or whether current prediction error changes the chosen winner. A small residual is not proof of identified host compute, transfer or pinning overhead.

**Falsifier/closing experiment.** On untouched build/workload cohorts, compare the current predictor, a simple active-bytes/bandwidth baseline and the frozen calibrated model. Reject extra model complexity if it fails to improve decision regret or safe-feasibility classification after its measurement cost. If an ostensibly held-out point can change any fitted term, the split contract fails.

### 2. Add one budgeted ask/tell sampler around the existing planner

**Change.** Use analytical feasibility and the current frontier to propose valid structured arms, then choose measured trials adaptively. Start with a coarse-to-local baseline modeled on Strata. Compare it with one optional Optuna TPE or SMAC adapter under the same elapsed-time budget, repeated workloads and quality gate. Keep conditional knobs engine-specific and distinguish immutable hardware scenarios from actions the launcher may execute.

**Reuse/seam.** `report.js:423–447,528–574` for candidate generation; `checkRecipe` and strict admission; `tools/record_run.py` for observations; `src/advisor.js` for bottleneck-sensitive neighborhoods. BoTorch/Ax is a later alternative if noisy constrained Pareto acquisition earns its larger setup cost. No solver should weaken engine capability or quality checks.

**Cost.** One adapter and serialization contract, persisted sampler state referencing existing ledger IDs, outcome fixtures and a budget-comparison experiment. With budget `B` and observed arm duration `T`, the affordable count is roughly `B/T`, not thousands of presumed free policy episodes. Include sampler/model-fitting CPU time and failed-arm time in `B`; measure package/environment friction before selecting a dependency. No second orchestrator is needed.

**Evidence gap.** The source does not establish which sampler is most sample-efficient on this conditional/noisy space, whether cheap fidelities preserve ranking, or whether a sophisticated sampler beats a small grid.

**Falsifier/closing experiment.** Compare incumbent feasible quality-qualified performance versus elapsed time, unsafe suggestions rejected before launch, wasted runtime and repeatability across held-out search seeds/workloads. Reject the adaptive dependency if coarse/local search matches it within measurement uncertainty at lower total cost. Reject fidelity pruning if full-length ranking reversals erase its savings.

### 3. Close planned-versus-effective placement and performance baselines

**Change.** Turn existing fallback/residency/capability evidence into a versioned, engine-specific allocation and execution contract. Distinguish capacity estimates, actual resident expert/KV/staging bytes, executed kernel paths and measured transfers. Compare the existing heat/quant planner against engine auto-fit, greedy VRAM-first and workload-weighted CPU-layer search. Validate dynamic-cache and network variants separately; do not infer them from static residency or a single local link rate.

**Reuse/seam.** Existing model intake, `context`, `checkRecipe`, expert-residency/fallback receipts and `record_run.py`; `winNetwork`, `networkTransfer` and network identity checks for multibox. Reuse actual llama.cpp/ik fit output as runtime evidence, GGUF parser as an independent accounting comparator and KTransformers/HybriMoE ideas only for applicable operator/cache paths. Feed identified measured curves into the existing window inputs instead of another runtime database.

**Cost.** Per-engine/build parsers and allocation/capability fixtures, passive evidence collection, then paired correctness/performance arms where authorized. Transfers need payload/protocol/direction/queue-depth-specific observations; quality-relevant kernel/draft changes need matched concurrent-path quality tests. Cross-box trials additionally consume every participating box's resources and energy, including idle power if that is the declared boundary. This is the highest measurement/integration cost of the three and can be staged by the most consequential unknowns.

**Evidence gap.** Backend names and catalog memory totals cannot establish allocatable live headroom, intended kernels or sufficient expert-cache residency. A model of a remote path does not establish its implementation or end-to-end benefit. Dynamic route heat may not transfer across workloads.

**Falsifier/closing experiment.** On matched requests, context/KV, quantization, concurrency and quality criteria, compare planner choices with the simple baselines. Count planned/effective placement disagreement before scoring speed. If engine fit or coarse/local tuning reaches the same feasible frontier with fewer measurements, simplify the planner. If network staging/RTT or quality regression consumes the projected gain, reject that distributed variant rather than crediting simulated throughput.

## 7. Questions for one design discussion

These are tractable design choices for the engineering team, not requests for credentials, hardware purchases or runtime authorization.

1. **Which decision is primary?** Per-client latency/accepted-token rate, total throughput, energy, or a declared Pareto set? What exact quality and resource limits define a feasible incumbent? This determines the sampler objective and valid workload mix.
2. **What is the immutable experiment identity?** Which built-data, calibration-split, workload and effective-engine fields must match before observations may transfer? Should window throughput checks that trained `eta` be relabeled or should `eta` be refit on training-only points?
3. **Which cheapest baseline must the next layer beat?** Existing analytical frontier plus local search, runtime `--fit`, and context-aware CPU-layer sweep should be specified before selecting a tuner. Choose one optional adapter by measured improvement per total evaluation cost, not framework popularity.
4. **What may be learned from unknowns?** Keep strict serving admission separate from explicitly authorized research probes. Specify how OOM, harness error, interference and numerical/quality failure enter the search history without pretending they are equivalent rewards.
5. **What contribution would survive an ablation?** If the heterogeneous tier/heat/quality/evidence integration is the contribution, publish the controlled comparison and reproducibility contract. Claim a novel algorithm only after a precise algorithmic difference and adequate prior-art comparison are demonstrated.
